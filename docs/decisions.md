# Решения и допущения

Что я решил сам там, где ТЗ не даёт однозначного ответа, и что сознательно не делал.

## Права и роли

1. **Роль хранится в `app_metadata` пользователя.** Её меняет только сервер, а `user_metadata`
   пользователь может править сам. При создании пользователя роль копируется в таблицу
   `profiles`. Если роль не указана, пользователь становится исполнителем (минимальные права).
2. **Все постановщики равноправны.** Каждый видит и меняет объекты и задачи любого другого.
3. **Постановщик не может делать переходы исполнителя**, например сам взять задачу в работу.
   Это ровно таблица переходов из ТЗ.
4. **Список пользователей (имя и роль, без email) виден всем авторизованным.** Он нужен для
   имён в истории и для выбора исполнителя. Email в `profiles` не хранится.
5. **Чужая или несуществующая задача для исполнителя выглядит одинаково:** «Не найдено или нет
   доступа», а при смене статуса — «Задача не найдена». Так не раскрывается, что задача вообще
   существует.
6. **Регистрация выключена на уровне Auth.** Пользователей создаёт seed-скрипт через Admin API,
   либо их можно завести вручную в Dashboard.

## Статусы и история

7. **Статус меняется только через функцию базы `change_task_status`.** Прямая запись колонки
   `status` запрещена в два слоя: права на колонки (grants) и триггер. Триггер срабатывает
   даже для сервисного ключа.
8. **«Принята» — финальный статус по смене статуса.** Повторно открыть принятую задачу нельзя,
   но её поля (название, описание, исполнитель) можно править, и каждая правка попадает в
   историю.
9. **Комментарий обязателен только при возврате на доработку**, это проверяет база. Через API
   комментарий можно передать к любому переходу, но в интерфейсе поле есть только у «Вернуть
   на доработку».
10. **История пишется только самой базой:** при создании задачи и внутри `change_task_status`
    (смены статуса), а правки полей фиксирует триггер в отдельной таблице `task_field_history`.
    Пользователи не могут вставлять, менять или удалять записи ни одной из двух таблиц через
    API. Изменение записи блокирует триггер даже для сервисного ключа.
11. **История хранит смены статуса, правки полей и отправку задачи в корзину / восстановление.**
    Для правки видно, кто, когда, какое поле и что было → что стало. Правки через Dashboard или
    сервисный ключ тоже записываются, автор у них «Система». Так нет споров, кто что поменял.
12. **Одновременные клики.** Если два пользователя одновременно меняют статус одной задачи,
    проходит одно изменение, второе получает «Этот переход статуса недоступен», и карточка
    обновляется.

## Объекты и задачи

13. **Исполнитель обязателен при создании задачи** и должен иметь роль «Исполнитель». Это
    проверяется в базе.
14. **Задачу можно редактировать (название, описание, исполнитель) в любом статусе, в том числе
    «Принята».** Объект задачи после создания изменить нельзя: ни в интерфейсе, ни через API.
15. **Удаление задачи — это корзина.** Задача получает отметку `deleted_at`, пропадает у всех,
    постановщик может восстановить её. История сохраняется, а удаление и восстановление
    записываются в неё. Физически удаляет только администратор.
16. **Удаление объекта — тоже корзина.** В корзину уходит сам объект, его задачи скрыты и
    возвращаются вместе с ним при восстановлении. Задачи, удалённые отдельно, остаются в
    корзине. Перед удалением интерфейс сообщает, сколько задач уйдёт вместе с объектом.
17. **Переназначение исполнителя записывается в историю.** Статус при этом не меняется. Новый
    исполнитель продолжает с текущего статуса, старый сразу теряет доступ к задаче и, если других
    задач в объекте у него нет, к объекту.
18. **Исполнитель видит в списке объектов число только своих задач**, постановщик — всех.
19. **Корзина доступна только постановщику.** Исполнитель не видит удалённое и не может ничего
    удалять или восстанавливать.
20. **Задачу нельзя восстановить, пока её объект в корзине.** Сначала восстанавливают объект.
    Автоматического восстановления объекта нет, чтобы ничего не вернулось неожиданно.
21. **Физически удалять данные может только администратор** (сервисный ключ). Пользователи
    такого права не имеют, это проверяется в базе.

## Интерфейс

22. **Интерфейс показывает только доступные действия.** Набор кнопок вычисляется по той же
    таблице переходов, что и в базе. Если статус успел смениться (кто-то другой уже
    отреагировал), база отклонит действие, интерфейс покажет понятное сообщение и обновит
    карточку.
23. **«Мои задачи» — только у исполнителя.** У постановщика вместо этого список объектов с
    задачами. Сортировка: сначала «На доработке» (требует внимания), потом «Новая», «В работе»,
    «На проверке», «Принята». Есть фильтр по статусу.
24. **Сообщения об ошибках на русском.** Коды ошибок базы переводятся в понятные тексты.

## Что не сделано (вне объёма 2–3 часов)

- Пагинация и поиск: списки небольшие, загружаются целиком.
- Обновление в реальном времени: чужие изменения видны после обновления данных (переход по
  страницам, возврат на вкладку).
- Загрузка файлов и фото, сроки и приоритеты задач.
- Очистка корзины из интерфейса: окончательно удалить данные может только администратор.
- Автор удаления объекта не сохраняется после восстановления, а удаление объекта не пишется в
  историю его задач (пока объект в корзине, автор и время видны в корзине).
- Управление пользователями из интерфейса и восстановление пароля. Пользователей заводит
  администратор.
- При повышении исполнителя до постановщика его текущие задачи не переназначаются
  автоматически.
- Разделение кода фронтенда на части: бандл ~600 kB, для внутреннего инструмента приемлемо.
