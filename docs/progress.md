## 2026-11-05 — Шаг 5: карточка задачи, смена статуса, история, «Мои задачи»

**Сделано**
- «Карточка задачи»: поля (описание, объект-ссылка, исполнитель, статус, автор, дата), блок
  действий строго по `getAvailableActions`, смена статуса только через RPC
  `change_task_status`; «Вернуть на доработку» — модалка с обязательным комментарием (≤ 2000);
  кнопки заблокированы, пока идёт запрос; исполнитель видит последний комментарий доработки.
- Постановщик: «Редактировать» (название, описание, исполнитель, объект) — если статус ≠
  «Принята»; «Удалить» с подтверждением — в любом статусе, после удаления — карточка объекта.
- История: по возрастанию `changed_at` (при равенстве — `id`), «Создана» / «из → в», кто,
  комментарий.
- «Мои задачи»: фильтр по статусу (по умолчанию «Все»), сортировка «На доработке», «Новая»,
  «В работе», «На проверке», «Принята», внутри статуса — новые сверху; пустые состояния.
- Доступность: строки таблиц больше не кликаются целиком — название стало ссылкой (клавиатура,
  скринридер, средняя кнопка мыши).

**Решения / отклонения**
- Спека §8.3 п.4 противоречила §12.2/§12.3 (удаление принятой задачи) — формулировка исправлена:
  «Удалить» в любом статусе, «Редактировать» — кроме «Принята».
- После ошибки смены статуса (`INVALID_TRANSITION`, `NOT_ALLOWED`, `TASK_NOT_FOUND`) карточка и
  история перезапрашиваются — кнопки приходят в соответствие с реальным статусом.
- Фильтр и сортировка «Моих задач» — на клиенте (пагинации нет, §12.14).
- Редактирование задачи — отдельная модалка (код создания шага 4 не тронут).

**Ревью:** frontend-code-reviewer — APPROVED (живая проверка трёх новых выборок под RLS).

**Гейты:** lint, typecheck, test (231), test:db (155), build — зелёные.

**Открыто (некритично)**
- `updateTask`/`deleteTask` считают успехом и 0 затронутых строк (RLS не даёт ошибки); для
  постановщика практически недостижимо.
- Модалка доработки может остаться в состоянии «открыта», если после ошибки действий не
  осталось, и всплыть при их возвращении — редкая последовательность.

## 2026-11-05 — Шаг 4: экраны объектов

**Сделано**
- Клиент Supabase типизирован (`createClient<Database>`).
- Слой данных: `objects-api`, `tasks-api`, `profiles-api` (единственные модули, импортирующие
  клиент) + хуки TanStack Query с ключами и картой инвалидации.
- «Список объектов»: таблица (название, адрес, число видимых задач), создание объекта
  (постановщик), пустые состояния.
- «Карточка объекта»: данные, редактирование и удаление с подтверждением «Будет удалено задач: N.
  Действие необратимо», список задач (исполнитель, бейдж статуса, дата), создание задачи с выбором
  только исполнителей; «Не найдено или нет доступа».

**Решения**
- Число задач — встроенный агрегат PostgREST `tasks(count)`; он выполняется под RLS задач, поэтому
  исполнитель видит число своих задач, постановщик — всех (проверено живым запросом под
  executor1).
- Некорректный UUID в URL (`22P02`) трактуется как «не найдено».
- Запись отправляет только колонки, на которые есть grant (узкие типы + явные литералы);
  сгенерированные `Insert`-типы не используются.
- Ошибки запросов — уведомлением через `useNotifyError`, мутаций — `onError: notifyError`.
- Списки отсортированы по `created_at desc`; пагинации нет (§12.14).
- В Vitest заданы фиктивные `VITE_SUPABASE_*` — тесты не ходят в сеть.
- `Select` исполнителя с `hideDetached: false` (иначе выпадающий список не открывается в jsdom).

**Процесс:** форматтер разработчика переформатировал приёмочный тест карточки объекта; автор
теста подтвердил — изменился только перенос строки, проверки те же.

**Ревью:** frontend-code-reviewer — APPROVED.

**Гейты:** lint, typecheck, test (159), test:db (155), build — зелёные.

**Открыто:** строки таблиц кликабельны только мышью (`<tr onClick>`) — для клавиатуры и
скринридеров сделать ссылку в ячейке названия (запланировано на шаг 5).

## 2026-11-05 — Шаг 3: seed-скрипт с демо-данными

**Сделано**
- `scripts/seed/`: чистый слой конфигурации (`seed-config`: аргументы, env, проверки),
  библиотека `runSeed` и CLI `seed.cli.ts`; npm-скрипт `seed`.
- Демо: 4 пользователя (§9), 3 объекта, 8 задач во всех статусах; задача «Армирование колонн
  6-го этажа» прошла цикл `rework → in_progress → on_review`; в ЖК «Северный парк» задачи обоих
  исполнителей; переходы делают оба постановщика. Статусы двигаются только через RPC от имени
  нужных пользователей — история настоящая.
- Приёмочный тест `tests/db/seed/` (31 тест): чистые проверки конфигурации и интеграция на
  локальной БД (создание, видимость исполнителей, история, повторный запуск, починка, `--reset`).

**Решения / отклонения**
- Точка входа `scripts/seed/seed.cli.ts` (а не `scripts/seed.ts`) — правило группировки файлов.
- Новая обязательная переменная `SUPABASE_ANON_KEY` — для входа под демо-пользователями.
- Env читается только из окружения или файла `--env-file <путь>`; корневой `.env` сам не
  читается. Не-локальный URL — только с `--yes`. Ключ service_role в любой `VITE_`-переменной
  (по имени, значению, префиксу `sb_secret_` или JWT-роли) — отказ до любых сетевых вызовов.
- Повторный запуск чинит пользователей (пароль, роль, `profiles.full_name` через service role —
  триггер профиля обновляет только роль). Объекты/задачи пересоздаются только с `--reset`
  (удаление от имени manager1 с проверкой числа удалённых строк).
- Поиск пользователей по email — постраничный `listUsers` (помечен `ponytail:`; при росте —
  фильтр admin API или SQL RPC).
- Если файл `--env-file` не существует, tsx/Node падает раньше скрипта (exit 9, сообщение Node) —
  безопасно, задокументировать в README.
- `npm run test:db` перезаписывает пароль локальных демо-пользователей тестовым; после тестов
  перезапустить `npm run seed`.

**Ревью:** backend-code-reviewer — APPROVED.

**Гейты:** test:db 155 (дважды), lint и typecheck (node) по `scripts`/`tests`, test, build —
зелёные.

**Решения / отклонения**
- Клиент Supabase пока нетипизированный; `createClient<Database>` — на шаге 4.

- Форма входа с `noValidate`, чтобы браузерная валидация не подменяла тексты Mantine.

## 2026-11-04 — Шаг 1: база данных, права доступа, смена статуса

**Сделано**
- 5 миграций (`supabase/migrations/`): схема (enum-ы, `profiles`, `objects`, `tasks`,
  `task_status_history`, индексы, RLS, column-level grants); хелперы доступа в схеме `private`;
  RLS-политики; триггеры защиты в глубину (§7); RPC `public.change_task_status`.
- Сгенерированы типы `src/shared/api/database.types.ts` (`npm run gen:types`).
- Фикстуры тестов БД `tests/db/fixtures/` и 6 приёмочных наборов: auth, profiles, visibility,
  writes, transitions (все 20 запрещённых пар, гонка), history (+ каскады).

**Решения / отклонения от спецификации**
- Параметры хелперов названы `p_task_id` / `p_object_id` (иначе `object_id` затеняется колонкой
  `tasks.object_id` и проверка всегда истинна).
- Добавлен хелпер `private.is_valid_transition` — единственный источник матрицы §5.7 для RPC и
  триггера.
- Роль в `profiles` синхронизируется ещё и при `UPDATE` `raw_app_meta_data`: GoTrue записывает
  `app_metadata` отдельным UPDATE после INSERT (supabase/auth#1280). Это же реализует повышение
  до постановщика через service key (§4).
- Вставка задачи от service_role без автора или с автором-не-постановщиком → `NOT_ALLOWED`.
- `TASK_ACCEPTED_READONLY` срабатывает на любой UPDATE принятой задачи, даже no-op.
- Права по умолчанию в схеме `public` отозваны у `anon`/`authenticated`; у `service_role`
  остаются (нужно тестам и seed, чтобы доходить до триггеров).
- `config.toml`: `[auth.email] enable_signup = true` — этот ключ включает сам email-провайдер,
  без него не работает вход по паролю; регистрацию закрывает `[auth] enable_signup = false`
  (проверено: `signUp`, OTP с созданием пользователя, анонимный вход — отклоняются). Спека §4
  уточнена. Локально `sign_in_sign_ups = 1000` (тесты логинят много пользователей; на облако
  не влияет).
- Ошибки RLS/grants отдаются как `42501`; бизнес-ошибки — `P0001` с кодом в `message`. Клиент,
  пишущий `status`/`author_id`, получает `42501` до срабатывания триггеров.

**Ревью:** backend-code-reviewer — APPROVED, включая живые пробы PostgREST: вложенные выборки
(`objects?select=*,tasks(*)` и т.п.) не раскрывают чужие задачи; `private` не доступна через
API; повышение роли через `user_metadata` не работает; 3 параллельных RPC → 1 успех.

**Гейты:** test:db 124/124 (стабильно, 3 прогона подряд), lint, typecheck (node), db lint —
зелёные. Фронтенд-гейты прогоняются вместе с шагом 2.

**Открыто (некритично)**
- Повышение исполнителя до постановщика не переназначает его текущие задачи.
- Сгенерированные типы показывают `status`/`author_id` как записываемые (генератор не видит
  column grants) — фронтенд не должен на это опираться.
